## 1. Bottom line

The four release-blocking UI defects reported for `3cf5092` are fixed in `61d596d` and are confirmed end to end through the real browser UI, not only through request-building unit tests:

1. plugin-source approvals and the “restore credentials” switch now reach both restore paths;
2. an already-extracted snapshot folder can be previewed and restored with normal integrity checks;
3. the backup success banner reports the real file and plugin-copy counts;
4. the backup tab no longer starts stuck in folder mode while targets are loading.

The local suite passes **190/190** on Windows with real Chrome, including the three browser user flows and the cross-site browser test. `npm run typecheck` and `npm run check:lib` pass. No new high-severity security regression was found in this round.

The original review of `61d596d` found two non-blocking residuals. Both were fixed in follow-up commit `6a5d693`: the expanded plugin card now counts skipped rows separately, and an extracted snapshot's `manifest.json` is stat-checked and bounded before it is read. Regression coverage was added for each.

The longer-standing boundaries remain: no automatic rollback after a host crash (manual rollback snapshot), in-memory archive processing, no plugin publisher signatures, a single vault-wide operation lock, and a browser C-01 test that stubs the host session. With the follow-up fixes, this review recommends **release within the stated security and usability boundaries**, but does **not** support saying every finding is “fully closed forever”.

## 5. P2 (fixed in `6a5d693`) — skipped rows were counted as “ready” inside the plugin card

### Reproduction

A restore returned one installed plugin and two skipped plugins:

```json
{
  "pluginResults": [
    { "name": "ok", "profile": "web", "status": "installed" },
    { "name": "skip-one", "profile": "web", "status": "skipped", "reason": "source-not-approved" },
    { "name": "skip-two", "profile": "web", "status": "skipped", "reason": "source-not-approved" }
  ]
}
```

The actual server-rendered markup of `RestorePanel` shows both of these strings in the same result:

```text
恢复完成：插件 1 成功，插件 2 跳过，文件 0 写入，耗时 0.4s
...
插件安装结果
3 个就绪，0 个失败
```

### Cause

`src/client/components/ResultSummary.tsx` correctly computes:

```ts
const skipped = rows.filter((x) => x.status === 'skipped').length
return { ok: rows.length - failed - skipped, failed, skipped }
```

But `src/client/components/RestorePanel.tsx` independently and incorrectly computes:

```ts
const failed = rows.filter((r) => r.status === 'failed').length
sub={tr('restore.resultDesc', { ok: rows.length - failed, failed })}
```

It subtracts only failures, so skipped rows land in `ok`.

### Impact and severity

- **Severity: P2**, usability / reporting correctness.
- No data loss, privilege escalation, or security bypass.
- It directly contradicts the release-note claim “skipped plugins are counted separately” and can make a partial restore look complete when the user expands the details.
- The main banner is correct, so this is a secondary summary rather than a false all-green state at the top of the page.

### Fix applied

`RestorePanel` now uses the shared `pluginCounts()` result and a `restore.resultDescWithSkipped` string, so the subtitle says `1 个就绪，0 个失败，2 个跳过`. A server-rendered component test asserts that exact text and rejects the old `3 个就绪` output.

The reviewed recommendation was:

```ts
const { ok, failed, skipped } = pluginCounts(result)
sub={skipped
  ? tr('restore.resultDescWithSkipped', { ok, failed, skipped })
  : tr('restore.resultDesc', { ok, failed })}
```

Add a browser/SSR assertion that opens the `插件安装结果` details and requires `1 个就绪` and `2 个跳过`.

## 6. P3 (fixed in `6a5d693`) — extracted-folder `manifest.json` was read before limits

`src/core/extracted-snapshot.ts` starts with:

```ts
const entries = [{ path: 'manifest.json', data: await readFile(join(dir, 'manifest.json')) }]
```

Only afterward does it walk `files/`, checking `maxEntries`, `maxEntryBytes`, and `maxTotalBytes`. Thus the top-level manifest itself has no size check before allocation, and the whole operation remains in memory.

### Impact and severity

- **Severity: P3**, local resource-exhaustion hardening gap.
- The import path must already be approved by `PathPolicy`, and the user must explicitly choose the folder.
- It does not bypass manifest integrity or allow writes outside the restore root.
- It belongs to the existing M-05 boundary: archive handling is bounded but not streaming.

### Fix applied

`packExtractedSnapshot()` now sends both the manifest and every `files/` entry through one bounded `readEntry()` helper. It first `lstat`s the path, rejects links and non-files, checks entry count, per-entry size and the remaining total budget, then reads the file and repeats the size checks against the actual bytes. Two regression tests cover `maxEntryBytes` and `maxTotalBytes` violations.

The complete streaming/repack redesign remains part of the documented M-05 boundary and is still out of scope for this patch.

## 7. Confirmed security boundaries that remain

These are deliberate, documented trade-offs after the previous rounds. They are not new regressions in `61d596d`.

### H-03 — crash recovery is manual

A failure inside the running process is journaled and rolled back. If the host process dies mid-restore, `restore-in-progress.json` survives; on next start the UI shows a red banner and a one-click path to the pre-restore rollback snapshot. It does **not** automatically apply that snapshot.

Residual risk: if the user ignores the banner, the half-applied state remains. If the restore was started with rollback disabled, no recovery snapshot exists.

### M-05 — archive processing remains in memory

The default uncompressed limit is one quarter of installed RAM, clamped to 256 MiB … 2 GiB − 1, and is shown in the restore UI. Per-entry, entry-count and path limits apply. It is still not streaming.

Residual risk: a snapshot near the limit can increase peak memory substantially, including the extracted-folder path (whose entries are now individually bounded).

### H-06 — approvals are source-bound, not signed

The user approves `profile:name#<hash-of-exact-source>`. Changing the source between preview and restore voids the approval. Non-npm/non-GitHub sources are flagged and start unchecked.

Residual risk: no publisher signature or trusted-publisher identity. A compromised trusted host can still serve a malicious package, and an approved upstream can change later.

### C-01 — browser fence tested, host session stubbed

The cross-site browser test covers credentialed CORS, preflights, no-cors GET, `text/plain` POST, no-cors `fs/mkdir`, and a cross-site form POST. All attack requests were refused; a same-origin control received 200.

Residual gap: the test replaces dsh’s real `connection.requestRejection()` with an allow-all stub, so it proves the plugin’s own fence but not the host’s real signed-cookie behavior. DNS rebinding in a real browser is covered only indirectly by forged-`Host` HTTP tests.

### M-02 — one vault-wide lock

Backup, restore, plugin retry, and snapshot delete share one cross-process lock. A second operation queues. This is stricter than the report’s per-target requirement, trading throughput for simpler safety.

### U-5 — encrypted snapshots from another machine

Their credential flag lives inside the encrypted payload and cannot be inferred from a storage listing. The UI may show no “contains credentials” tag until the snapshot is previewed/restored. This is an information-display limitation, not a confidentiality failure.

## 11. Release recommendation

**Go within the stated boundaries.**

`61d596d` fixed the four P1 UI blockers that made the preceding round incomplete. `6a5d693` then closed the two P2/P3 residuals found by this review. Real browser tests exercise the exact click → request → server → result path that previously failed, and the full 193-test suite is green locally on Windows with Chrome; the changes are type-, build-, and `lib/`-consistent.

The P2 subtitle count and P3 manifest read-order hardening are fixed in `6a5d693`, with three new regression assertions (one UI and two archive-limit tests). The full local run after those changes is 193/193, including the real-browser flows.

The release notes should keep the honest boundaries:

- recovery after a host crash is a guided manual rollback, not automatic;
- snapshots are still unpacked in memory with RAM-based limits;
- plugin approvals bind the exact source but do not verify publisher signatures;
- the browser C-01 test proves the plugin fence with a stubbed host session;
- one vault-wide operation lock serializes all writes;
- encrypted snapshots from another machine cannot advertise their credential flag before decryption.

`6a5d693` is suitable for the next external review and for release within those stated constraints. It should not be described as “all findings fully resolved with no remaining caveats”.
