# Security fixes for the 2026-10-20 audit

The audit was run against commit `aff0476` and scored 38/100 ("Blocked"). This document lists every finding ID in that report (C-01 … L-04). For each one it gives the fix and the regression test that guards it. Unless noted otherwise, the tests are in `tests/security-audit-2026-10-20.test.ts`, under a `describe()` block named after the ID.

Run them with `npm test`. CI runs them on Node 24 on ubuntu-latest and windows-latest.

## Changes users will notice

- **Opening the plugin page needs a dsh session.** The browser UI uses dsh's own session cookie, which is set when you open the URL `dsh web` prints (`/?token=…`) or launch Desktop. There is no extra token to copy. Scripts that called `/api/dsh-vault/*` with plain `curl` now need that cookie plus `x-dsh-vault-request: 1` and `content-type: application/json`. The CLI (`dsh-vault …`) is unchanged.
- **Export targets** must be in your home folder, on another drive or a removable disk, or in a folder chosen with the system picker. Overwriting an existing export asks for confirmation.
- **Restore stops on links.** If part of your dsh home is a symlink or junction (for example `~/.dsh/skills` pointing into a dotfiles repo), restore refuses and changes nothing. Replace the link with a real folder, or restore with the CLI into a sandbox `--home`.
- **Credentials are restored only when "Restore credentials" is on.** It is on by default, and only appears for encrypted snapshots that contain credentials.
- **Git, tarball and URL plugin sources** in a snapshot need a checkbox. They are unchecked for imported files. Plugin lifecycle scripts are disabled for the installs dsh-vault runs during restore (`--ignore-scripts`; since the final round also `npm_config_ignore_scripts` for the dsh CLI fallback, and the host plugin manager is no longer used), so a plugin that needs a build step must be rebuilt by hand.
- **Plaintext backups drop `user:token@` from git URLs.** A private git plugin needs its credentials set up again on the new machine. The pre-restore rollback follows the same rule.
- **Plaintext plugin copies omit `*.pem` / `*.key` files.** These now count as credentials. Use an encrypted backup with credentials to keep them.

## Not addressed / partial

_Status as of the re-audit round; the final round below supersedes the H-03, M-05, H-06, C-01, L-03 and L-04 entries._

- **M-05 streaming decompression.** Decompression is still in memory, now with hard limits on output size, entry size, entry count and path length; it is not streaming.
- **H-03 staged atomic replace.** Writes are journaled and reverted on failure, but there is no "stage everything, then rename" step. A crash of the host process mid-restore is not reverted automatically; the encrypted or plaintext pre-restore rollback snapshot covers that case.
- **H-06 source allow-list and full integrity / signatures.** Approval is per plugin rather than a host allow-list. Integrity is still checked only where the registry provides it, as before.
- **M-02 per-target locks.** There is a single vault-wide lock rather than one lock per target, which is stricter.
- **C-01 browser end-to-end attack.** The attack page was not run in a real browser. The fence was verified with forged-header HTTP probes and by the legitimate same-origin UI against a real `dsh web`.

## Usability round (review of 3cf5092, real-browser user testing on Windows)

Tests: `tests/ui-contract-2026-10-20.test.ts` runs on both OSes. It drives the browser `VaultApi` client against the real routes and records the bodies it sends. `tests/browser-e2e-ui.test.ts` loads the real `VaultApp` in headless Chrome, clicks through the UI and checks the request bodies and results. That test runs on ubuntu CI and is skipped where Chrome isn't installed.

**Correction to F-5.** The review found that F-5's claim did not hold in the UI. A plugin source the user checked never reached the server, so H-06 approval did not work in the browser (it failed closed). While fixing this we also found that F-5's server-side claim ("the HTTP API accepts only source-bound keys") held only for `POST /jobs/restore`. The synchronous `POST /restore` route passed `*` and `profile:name` through unchanged. Both are fixed below (U-1).

| Finding | Cause | Fix | Test |
|---|---|---|---|
| **U-1** (P1) Checking a plugin source in the restore dialog never approved it | `RestorePanel` built `approvedPluginSources`, but `VaultApp` rebuilt the request field by field and dropped it. The API client's type didn't list it either. | A single `RestoreRequestBody` type (`src/client/lib/requests.ts`) is used from panel to app to API client. The panel builds the body with `buildRestoreRequest()`, and `VaultApp` passes it on unchanged. `sanitizeApprovals()` now also runs on `POST /restore`. | Node: `buildRestoreRequest()` sent through `VaultApi.startRestoreJob` reaches the server with the source-bound key, and the source is attempted. Unchecked, it is `source-not-approved` and never fetched. `POST /restore` ignores `*` / `web:evil`. Browser: after the user clicks the checkbox, the sent body contains `web:evil#<hash>` and the source is attempted. With the old forwarding put back, the browser test fails. |
| **U-2** (P1) The "restore credentials" switch never sent `includeSecrets` | Same cause as U-1. | Same fix as U-1. | Node and browser: the body has `includeSecrets: true`, `.credentials.yaml` is rewritten and listed in `credentialsWritten`. Off: `credentialsWritten: []` and the local file is unchanged. |
| **U-3** (P1) Importing an extracted snapshot folder failed with `incorrect header check (HTTP 500)` | The folder adapter treated every `*.json` (here `manifest.json`) as a snapshot archive. | A folder holding `manifest.json` and an optional `files/` is read as an extracted snapshot (`src/core/extracted-snapshot.ts`): links and special files are refused, and archive limits apply. It is then repacked in memory and goes through the normal verified unpack (manifest integrity, per-file sha256 and size). `.json` files no longer count as snapshot files in folders or as import files. Bad input (not gzip, bad manifest, checksum mismatch) is now `400 BAD_SNAPSHOT`, and a folder without a snapshot is `404` with a readable message. | Node: an extracted folder previews and restores. A folder with a random `manifest.json` gets 400 and one with only `*.meta.json` gets 404. Browser: the folder previews with no error banner. |
| **U-4** (P1) The backup success banner always showed 0 files and 0 plugin copies | The API trims manifests (H-04) to `fileCount` and `{name, profile}`, but the banner still read `manifest.files` / `fallbackBundle`. | `publicResult()` adds `pluginCopyCount` and a per-plugin `hasCopy`. The banner uses `backupCounts()`, which reads the trimmed fields and still accepts a full manifest. | Node: the real backup's `fileCount` is shown, and the copy count is right for a trimmed result. Browser: the number of files in the banner equals the file count in the snapshot's manifest. |
| **U-5** (P2) Snapshot list said "no credentials" for encrypted snapshots that have them | Storage listings can't see inside encrypted files, so the value was hard-coded `false`. | Each snapshot made on this machine records its credentials flag in `snapshot-index.json` in the data folder, and listings use that. **Limit:** an encrypted snapshot made on another machine still shows "no" until restored, because the flag is inside the encryption. | Node: an encrypted + credentials backup is listed with `includeSecrets: true`; plaintext snapshots never are. |
| **U-6** (P2) The restore result counted skipped plugins as successes | The headline subtracted only failures. | `pluginCounts()` separates ok / failed / skipped. The headline shows "插件 N 跳过" separately, and skipped rows show their localized reason. | Node: 1 installed + 2 skipped gives "插件 1 成功" and "插件 2 跳过". |
| **U-7** (P2) Plaintext backup showed the "凭据" category as checked | The category set started with every category. | Without encryption the category is unchecked and locked, with a hint, and it is never sent. | Covered by the backup body in the browser flow (plaintext, no `credentials` category). |
| **U-8** (P2) `nextRunAt` stayed set after disabling the schedule | Only the timer was stopped. | `updateSettings()` drops `nextRunAt` whenever the schedule is disabled, and a run that finishes after disabling doesn't set it again. | Node: enable with a future `nextRunAt`, then disable; `getSchedule()` and `status()` have no `nextRunAt`. |
| **U-9** (P3) English and technical text in the Chinese UI | — | The default target "Local folder" is shown as 本地目录. Path-policy and snapshot errors are localized by error code (`localizeError()`), with the raw path kept. Dates follow the UI locale everywhere, including the H-03 banner, which showed an ISO timestamp. Durations under 10 s show tenths instead of `0s`. Switching the restore source clears the previous result banner. | Node: localized private-folder error, `BAD_SNAPSHOT`, target name and duration format. |
| **U-10** Backup tab sometimes stuck on "folder" mode on first open | Found while writing the browser test: the destination mode was chosen before targets loaded, so a slow `/status` left it on "folder". | The panel switches to the storage target when targets arrive, unless the user already picked a mode. | The browser backup flow, which clicks backup without choosing a destination. |

**Not changed in this round:** plugin descriptions (they come from each plugin's own `package.json`), the profile name `web` and the cipher name `scrypt + AES-256-GCM`, which are identifiers. M-02 stays a single vault-wide lock: one backup, restore or plugin retry runs at a time across UI, schedule, tools and CLI, and a second waits. This is stricter than per-target locks, at the cost of throughput. H-03, M-05, H-06 and C-01 keep the boundaries stated in the final round: no automatic crash rollback, in-memory decompression, no signatures, and a stubbed host session in the browser test.
