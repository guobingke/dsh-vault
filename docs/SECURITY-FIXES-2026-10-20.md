# Security fixes for the 2026-10-20 audit

The audit was run against commit `aff0476` and scored 38/100 ("Blocked"). This document lists every finding ID in that report (C-01 … L-04). For each one it gives the fix and the regression test that guards it. Unless noted otherwise, the tests are in `tests/security-audit-2026-10-20.test.ts`, under a `describe()` block named after the ID.

Run them with `npm test`. CI runs them on Node 24 on ubuntu-latest and windows-latest.

| **C-01** Local API callable cross-origin; exfiltration chain | Every `/api/dsh-vault/*` route (including `GET /jobs`, `/status`, `/plugins`, `/fs/*`, `/schedule/run`) goes through `rejectRequest()` in `src/api/http.ts`: (1) the socket must be loopback; (2) the `Host` must be `127.0.0.1` / `localhost` / `[::1]`, which blocks DNS rebinding; (3) `Sec-Fetch-Site` must be `same-origin` or `none`; (4) any `Origin` must equal the Host; (5) the `x-dsh-vault-request: 1` header is required, so a cross-origin page needs a CORS preflight, which is never granted; (6) `POST`/`PUT` bodies must be `application/json`, so the `text/plain` "simple request" is refused with 415; (7) dsh's own browser session check `connection.requestRejection(req)` must pass. That check uses the signed `HttpOnly`, `SameSite=Strict` `dsh-auth-*` cookie that dsh issues for the launch token. `src/index.ts` injects dsh's `connection` service. Without it, the API fails closed with 503. The CLI and tools are unaffected. | `C-01 …`: missing session → 401; no marker → 403; `Origin: http://evil.example` → 403; `Sec-Fetch-Site: cross-site` / `same-site` → 403; rebinding `Host: evil.example` → 403; `text/plain` `POST /targets` (the audit repro) → 415 and no target stored; every route × method is 401/405 without a session; no authenticator → 503; `apply()` wires `connection.requestRejection` into the routes. ## Changes users will notice

- **Opening the plugin page needs a dsh session.** The browser UI uses dsh's own session cookie, which is set when you open the URL `dsh web` prints (`/?token=…`) or launch Desktop. There is no extra token to copy. Scripts that called `/api/dsh-vault/*` with plain `curl` now need that cookie plus `x-dsh-vault-request: 1` and `content-type: application/json`. The CLI (`dsh-vault …`) is unchanged.
- **Export targets** must be in your home folder, on another drive or a removable disk, or in a folder chosen with the system picker. Overwriting an existing export asks for confirmation.
- **Restore stops on links.** If part of your dsh home is a symlink or junction (for example `~/.dsh/skills` pointing into a dotfiles repo), restore refuses and changes nothing. Replace the link with a real folder, or restore with the CLI into a sandbox `--home`.
- **Credentials are restored only when "Restore credentials" is on.** It is on by default, and only appears for encrypted snapshots that contain credentials.
- **Git, tarball and URL plugin sources** in a snapshot need a checkbox. They are unchecked for imported files. Plugin lifecycle scripts no longer run during restore (`--ignore-scripts`), so a plugin that needs a build step must be rebuilt by hand.
- **Plaintext backups drop `user:token@` from git URLs.** A private git plugin needs its credentials set up again on the new machine. The pre-restore rollback follows the same rule.
- **Plaintext plugin copies omit `*.pem` / `*.key` files.** These now count as credentials. Use an encrypted backup with credentials to keep them.

## Not addressed / partial

- **M-05 streaming decompression.** Decompression is still in memory, now with hard limits on output size, entry size, entry count and path length; it is not streaming.
- **H-03 staged atomic replace.** Writes are journaled and reverted on failure, but there is no "stage everything, then rename" step. A crash of the host process mid-restore is not reverted automatically; the encrypted or plaintext pre-restore rollback snapshot covers that case.
- **H-06 source allow-list and full integrity / signatures.** Approval is per plugin rather than a host allow-list. Integrity is still checked only where the registry provides it, as before.
- **M-02 per-target locks.** There is a single vault-wide lock rather than one lock per target, which is stricter.
- **C-01 browser end-to-end attack.** The attack page was not run in a real browser. The fence was verified with forged-header HTTP probes and by the legitimate same-origin UI against a real `dsh web`.

| **R-2** M-02 lock could be stolen from a live owner and released by a non-owner | `OperationLock` rewritten. The lock file holds `{pid, host, nonce (128-bit random), op, startedAt, heartbeatAt}`; the holder touches its mtime every 30 s while running. It is abandoned only when the owner is on this host and its pid is dead, or (other host) neither `heartbeatAt` nor the mtime moved for 10 min. A live same-host owner is never taken over, whatever its age. Takeover renames the judged file to a tombstone, re-checks the tombstone still carries the judged nonce (puts it back otherwise), and then competes through the exclusive `wx` create. Release reads the file, renames it to a tombstone only if the nonce is ours, and restores it if the tombstone turns out not to be ours. | `re-audit 2 …`: a live pid with mtime 1970 and `staleMs: 1` keeps its lock (`VAULT_BUSY`); dead pid and stale foreign host are taken over, fresh foreign host is not; the record carries host/pid/nonce, the heartbeat touches the file, and a release leaves another owner's lock in place. |
| **R-3** H-03 plugin phase not covered by the rollback | Decision: individual plugin install failures are a **partial success by design** — the restored config stays, failures are listed (`ok: false`, `pluginsFailed`, exit code 2 in the CLI) and can be retried. But the restore now owns the write journal across all phases: if anything after the file apply throws (re-applying this machine's own entry, the plugin phase, saving the restore record), every restored file is reverted and the restore fails with `RESTORE_ROLLED_BACK`. | `re-audit 3 …`: an abort thrown during the plugin phase leaves `settings.yaml` as before and removes the added file; a plain plugin failure keeps the restored `settings.yaml` and reports `ok: false`. |
| **R-4** `check:lib` could fail on a Windows clean build | Output is byte-deterministic across OSes: `tsconfig.json` sets `"newLine": "lf"`; `.gitattributes` adds `* text=auto eol=lf` (checkouts are LF on Windows too); `scripts/build-utils.mjs` `normalizeText()` strips BOM and CRLF from CSS and the bundle; `cssTagId()` is path-separator independent; `copy-assets` normalizes `theme.css`. `build-client.mjs --out <file>` builds to a scratch path. | `re-audit 4 …`: `normalizeText`/`cssTagId` unit tests, `newLine: lf` asserted, and a fresh client bundle is compared byte-for-byte with the committed `lib/client.js` — this runs in the existing test job on both ubuntu and windows (no workflow change). |
